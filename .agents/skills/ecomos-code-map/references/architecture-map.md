# EcomOS architecture map

Verified against the repository at release candidate 1.0.0-rc.2. Re-check paths before relying on them after big refactors.

## Apps and packages

| Path | Role |
|---|---|
| `apps/storefront` | Next.js 16 storefront. `src/app` routes, `src/features/*` (about, account (disabled), auth (disabled), brand(s), cart, catalog, checkout, contact, content, i18n, landing, layout, menu, product, rfq), `src/components`, `src/lib`, `src/stores`, `src/i18n`, `e2e/`. |
| `apps/storefront/src/lib/engine.ts` | The only file allowed to import an engine adapter. |
| `apps/storefront/src/lib/client-profile.ts` | Resolves the active `ClientProfile` and theme from `ECOM_CLIENT_PROFILE` and `THEME_NAME`. Registries come from `clients.generated.ts` (generated by `scripts/generate-clients.mjs`), so adding a client edits no core file. The default key is still `paraloca` when `ECOM_CLIENT_PROFILE` is unset. |
| `apps/storefront/src/lib/runtime-config.ts` | `validateRuntimeConfig`: production fail-fast for required env. |
| `apps/storefront/src/lib/addon-route-guard.ts`, `capabilities.ts`, `addon-capabilities.ts` | Capability and addon gates; off addons return 404. |
| `apps/storefront/src/addons.generated.ts` | Generated by `scripts/generate-addons.ts` from `ADDONS`. Do not hand-edit. |
| `packages/ecom-engine` | `interface.ts` (EcomEngine contract), `types.ts`, `fake-engine.ts`, `factory.ts`, addon registry and manifest schema, `search/` provider contract. |
| `packages/engine-woocommerce` | WooCommerce adapter: `rest.ts`, `graphql.ts`, `mappers.ts`, `money.ts`, `currency.ts`, `products.ts`, `cart.ts`, `checkout.ts`, `checkout-attempts.ts` (durable idempotent checkout, order recovery), `orders.ts`, `brands.ts`, `content.ts`, `client.ts`. |
| `packages/addons-rfq`, `addons-i18n`, `addons-multi-payment` | Addons. Each exports `register` and `disable`, has `manifest.json`. |
| `packages/brand-config` | `ClientProfile` schema and loader. |
| `packages/themes` | Theme tokens; `src/clients/<id>/theme.ts`. |
| `packages/cli` | Starter CLI (`theme`, `cms`). The `provision` command is not registered (see `operations/PROVISION.md`). |
| `clients/<id>` | Client profile, content schema, approval records, RFQ policy. |
| `plugins/` | WordPress PHP plugins: `wp-ecomos-rfq` (quotes, offers, conversion), `wp-ecomos-addons` (addon lifecycle and migration guard), `wp-ecomos-operations`, plus older epioso plugins. `plugins/wordpress-mcp` is a separate submodule: do not modify it. |
| `scripts/` | Guard, generators (`generate-addons.ts`, `generate-tokens.ts`), probes, restore isolation, `ecomos-release.mjs`, `ecomos-upgrade.mjs`. |
| `.agent-hub/` | Multi-agent coordination (tasks, claims, verification). Shared by all providers; do not create a second board. |
| `docs/ecomos/` | INSTALL, EXTENDING, CHANGELOG, MIGRATIONS, FIX_LEDGER, UPDATING_INSTANCES, PROGRESS, release and evidence records. |

## Data flow for a guest purchase

Browser -> storefront route/action -> `lib/engine.ts` -> WooCommerce adapter -> WooCommerce Store API (authoritative cart and totals) -> order. The checkout attempt store (`checkout-attempts.ts`) keys retries by owner plus operation so a repeat submit never creates a second order and never leaks another guest's order. Order confirmation is read back with a grant token.

## Data flow for a quote (RFQ addon on)

Quote basket (browser) -> `/api/rfq` -> WordPress RFQ plugin tables (`ecomos_rfq_quotes`, revisions) -> staff revises an offer -> guest reviews and accepts with a hashed access secret -> staff conversion creates exactly one WooCommerce order, idempotent on replay.

## Generated and ignored files

Generated: `addons.generated.ts`, theme token CSS. Ignored: `.env.local`, `.next`, `node_modules`, `.agent-hub/.runtime`. Never commit secrets or runtime output.
