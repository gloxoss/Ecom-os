## Migration note for 1.0.0-rc.8

- **WordPress companion plugin: wp-ecomos-operations.** Instances updating to 1.0.0-rc.8 must install/update and activate `plugins/wp-ecomos-operations` on the WordPress backend. The plugin introduces `order-recovery.php`, which hooks Store API and traditional checkout order creation to save indexed metadata `_ecomos_attempt_id`, and exposes an authenticated REST route `GET /wp-json/ecomos/v1/orders/by-attempt/<id>`.
- **Database & HPOS.** HPOS-safe and legacy-safe: metadata is stored via `$order->update_meta_data()` in `wp_wc_orders_meta` (or postmeta on legacy). Back up the database before updating companion plugins. No migration queries or table alters required.
- **Connector permissions.** The route requires the read-only connector capability `read_private_shop_orders`. The baseline connector role documented in `INSTALL.md` already includes this capability. Guest and unauthorized requests receive 401/403.
- **Engine behavior.** `findOrderByAttemptCorrelation` in `@ecom-os/engine-woocommerce` checks `GET /wp-json/ecomos/v1/orders/by-attempt/<id>` first. If the route returns 404 (`rest_no_route`, older backend without the plugin), it gracefully falls back to the legacy paginated customer_note scan up to the 1,000 order cap. The caller's billing email ownership barrier is strictly enforced.
- **Confirm.** Run `node plugins/wp-ecomos-operations/tests/order-recovery.spec.mjs`. In the storefront, check that `_ecomos_attempt_id` is populated in `wp_wc_orders_meta` upon checkout.
- **Rollback.** Revert the plugin update or deactivate `wp-ecomos-operations`. The storefront will fall back to paginated scanning.

- **Fixed (Engine):** `findOrderByAttemptCorrelation` prioritizes direct indexed order lookup via REST route (< 500 ms at scale) with graceful fallback to capped scanning on older backends; hardened against mid-checkout crashes, duplicate submissions, and email mismatches.
