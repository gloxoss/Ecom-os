## Migration note (next release)

- **What changed.** `apps/storefront/src/styles/brand.tokens.css` and `apps/storefront/src/styles/theme-vars.css` are now both generated, from one resolution, by `scripts/brand-styles.ts`. The repo-root `scripts/generate-tokens.ts` and the storefront's `scripts/generate-theme.ts` are both thin entry points into it, so whichever one the build runs, the output is identical. `packages/brand-config/src/tokens.ts` exports `generateBrandCss()` in place of `generateTokensCSS()`.
- **Who is affected.** Every instance. No instance file needs editing: the entry points kept their names and their `predev`/`prebuild` wiring, so `pnpm dev` and `pnpm build` produce the same two files as before.
- **Exact steps.** Nothing to run by hand. `tsx scripts/generate-tokens.ts` (repo root) or `tsx scripts/generate-theme.ts` (from `apps/storefront`) each regenerate both stylesheets.
- **How to confirm.** `apps/storefront/src/styles/brand.tokens.css` ends with `--brand-primary: hsl(var(--primary));` and `theme-vars.css` declares `--primary`. Changing a colour in `brand.config.ts` and regenerating must move both values.
- **How to roll back.** Revert the commit. The two stylesheets return to their committed values and the entry points to their old bodies.
- **Two value changes to expect in the generated diff, neither visible on screen.** (1) The six colours a client sets are now emitted as unrounded HSL triplets; the previous whole-number triplets were lossy, so `--primary: 30 73% 38%` rendered `#a8611a` where the brand file says `#aa631a`. The unrounded triplet renders `#aa631a` exactly. (2) `theme-vars.css` now writes `--radius: 16px` instead of `1rem` (the resolver prefers the profile's `radii.md`); those are the same length at a 16px root, and no stylesheet or component reads `--radius`.

## Changelog line

- Theming: one source of truth for page colours. `brand.config.ts` plus the active theme now generate both the Tailwind tokens and the theme CSS variables from a single resolution, so a client sets its colours once and the two systems cannot disagree.

## Owner decision needed — widen the palette to Tailwind? (ledger row 21)

The theme registry defines 19 colour tokens. Before this change Tailwind exposed 6 of them, and that is still true. The consequence is that the following classes are written across the storefront but produce no CSS today: `border-border` (42 usages), `bg-input` (22), `text-destructive` (23), `ring-ring` (9), `bg-card` (6), and the `*-foreground` variants.

Wiring them into `@theme` is a one-line change per token, but it is not a neutral one: elements that currently inherit their colour would suddenly pick up the theme's value, and `border-border` alone would put a visible border colour on the header, footer and RFQ banner. That is a change to the starter's default look, which ECO-1501 was explicitly told not to make.

So the decision belongs to the owner:

1. **Leave as is.** The 13 tokens are generated and available as CSS variables; nothing new is exposed to Tailwind. No visual change anywhere.
2. **Expose them in a follow-up task**, accept the Angelina re-render, and review the starter's default pages with screenshots at that point.

Recommendation: option 2 as its own task, so the visual review is deliberate rather than a side effect of a theming refactor.
